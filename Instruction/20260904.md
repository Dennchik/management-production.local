1. Производственные объекты

   Нам нужна универсальная сущность, условно:

   ProductionItem

   Она представляет объект, который может участвовать в производстве.

   Например:

   Бумага ВП 60
   ```
	Плёнка FPO
	
	Клей
	
	Колесо
	
	Рама
	
	Седло
	
	Окрашенная рама
	
	Велосипед
	```
   При этом существующий Material не уничтожаем.

   Он остаётся складским справочником материалов:
   ```
	materials
	
	↓
	
	material_rolls
	```
   А production получает возможность работать как с материалами, так и с полуфабрикатами/изделиями.

2. Операция

   Оставляем:
   ```
	production_operations
	```
   Она содержит только определение операции:
   ```
	id
	
	name
	
	code
	
	description
	
	is_active
	```
   Например:
   ```
	id: 15
	
	name: Ламинация
	
	code: LAM
	```
   Но для системы это просто пользовательская операция.

   Она не содержит никаких специальных полей:
   ```
	lamination_...
	
	cutting_...
	
	printing_...
	```
   И тем более никаких условий по названию.

3. Состав операции

   Вот этого сейчас не хватает.

   Создаём:
   ```
	production_operation_inputs
	
	production_operation_outputs
	```
   Но эти таблицы нужно понимать как технологическую спецификацию операции, а не как фактический расход.

   Поэтому я предлагаю разделить:
   ```
	Operation
	
	│
	
	├── Input specification
	
	└── Output specification
	```
   и отдельно:
   ```
	Operation Execution
	
	│
	
	├── Actual input
	
	└── Actual output
	```
4. Технологический вход операции

   Новая сущность:
   ```
	production_operation_input_specs
	```
   Например для операции:
   ```
	Изготовление колеса
	```
   может быть:
   ```
	Обод × 1
	
	Спица × 36
	
	Камера × 1
	
	Покрышка × 1
	```
   Для ламинации:
   ```
	Бумага × 1
	
	Плёнка × 1
	
	Клей × 1
	```
   Для финальной сборки:
   ```
	Рама × 1
	
	Колесо × 2
	
	Руль × 1
	
	Седло × 1
	```
   Операция при этом совершенно универсальна.

5. Технологический выход

   Аналогично:
   ```
	production_operation_output_specs
	```
   Например:
   ```
		Изготовление колеса
			  ↓
		Колесо × 1
	```

   или:
   ```
	Финальная сборка
			  ↓
	Велосипед × 1
	```
   или:
   ```
	Ламинация
			  ↓
	Ламинированный полуфабрикат × 1
	```

6. Маршрут

   Существующая схема:
   ```
	production_routes
			  ↓
	production_route_steps
			  ↓
	production_operations
	```

   Оставляем.

   Например: пользователь сам создаёт маршрут.

   Маршрут: Производство велосипеда
   ```
	Шаги:
	
	1. Изготовление колеса
	
	2. Изготовление рамы
	
	3. Изготовление седла
	
	4. Покраска
	
	5. Сборка
	```
   Другой пользователь может создать совершенно другой маршрут:

   Производство печатной продукции
   ```
	1. Ламинация
	
	2. Праймирование
	
	3. Резка
	
	4. Печать
	
	5. Сборка
	```

   Для БД это просто:

   ```
	Route
	 ├── Step 1 → Operation A
	 ├── Step 2 → Operation B
	 ├── Step 3 → Operation C
	 └── Step 4 → Operation D
	```

7. Производственное задание

   Существующий:

   ```
	production_jobs
	```

   Оставляем, но меняем принцип определения продукта.

   Сейчас:

   product_name

   не подходит.

   Нужно:

   ```
	product_item_id
	```

   То есть:

   ```
	ProductionJob
			↓
	ProductionItem
	```

   Например:
   ```
	Задание №JOB-0001
	Маршрут: Производство велосипеда
	Продукт: Велосипед
	Количество: ...
	```
8. Выполнение операции

   Существующий:

   ```
	production_operation_executions
	```

   оставляем.

   Получаем:

   ```
	ProductionJob
			↓
	RouteStep
			↓
	OperationExecution
	```

   Например:
   ```
	JOB-0001
		 ↓
	Шаг 4 — Покраска
		 ↓
	Execution #1
	```

   Если операцию нужно выполнить несколько раз, остаются:
   ```
	execution_number = 1
	execution_number = 2
	...
	```
   Это уже хорошая универсальная конструкция.

9. Фактические входы

   Вот здесь нужно отделить спецификацию от факта.

   Например: спецификация говорит.
   ```
	Покраска:
	
	Вход:
	
	Рама × 1
	
	Краска × 0.5 кг
	```
   А фактически оператор использовал:
   ```
	Рама №R-102
	
	Краска из MaterialRoll №58
	
	Фактически 0.63 кг
	```

   Поэтому фактический input должен позволять указать:

   ```
	ProductionItem
	
	+
	
	конкретную физическую единицу, если она существует
	
	+
	
	фактическое количество
	
	+
	
	отход
	
	```

   Для складского материала физической единицей может быть:
   ```
	MaterialRoll
	```

   Для другого производственного объекта это может быть уже другая сущность.

10. Фактические выходы

    То же самое.

    Спецификация:
    ```
	 Покраска
		  ↓
	 Окрашенная рама × 1
	 ```
    Факт:
    ```
	 Получено:
	 
	 Окрашенная рама
	 
	 конкретный экземпляр №PF-102
	 ```
    А если операция производит складской материал в рулоне, тогда результат может быть связан с конкретным складским
    рулоном.
    То есть roll_id становится деталью физического учёта, а не фундаментом production-модели.

12. Что произойдёт с существующими таблицами

    Не будем хаотично удалять всё.

    Оставляем:
    ```
	 production_operations
	 
	 production_routes
	 
	 production_route_steps
	 
	 production_jobs
	 
	 production_operation_executions
	 ```

    Переделываем:
    ```
	 production_operation_inputs
	 
	 production_operation_outputs
	 ```
    потому что сейчас они одновременно пытаются быть и спецификацией, и фактическим движением.

    Добавляем:
    ```
	 production_items
	 
	 production_operation_input_specs
	 
	 production_operation_output_specs
	 ```

    При этом склад остаётся отдельным:
    ```
	 materials
		  ↓
	 material_rolls
		  ↓
	 receipts / issues
	 ```
    А production сможет использовать складские объекты через универсальную связь.

13. Очень важный момент: ProductionItem не должен дублировать Material

    Я бы не делал копию всех полей Material в production_items.

    Например:
    ```
	 Material
	 ----------------
	 id
	 name
	 code
	 grammage
	 thickness
	 format
	 identifier
	 ...
	 ```
    Остаётся именно складским справочником.

    А ProductionItem должен отвечать за производственную сущность.

    Нужно будет определить связь примерно такого характера:

    ```
	 ProductionItem
		  │
		  ├── material_id        → если это складской материал
		  │
		  └── собственные данные → если это полуфабрикат/изделие
	 ```
    Но здесь есть ещё один архитектурный вопрос, который лучше решить сейчас, до написания миграций.

    Нужно определить, что именно является универсальным объектом:

    Вариант А
    ```
	 production_items
	 ```
    Одна универсальная таблица:
    ```
	 сырьё
	 полуфабрикат
	 изделие
	 ```
    Вариант Б

    отдельные справочники:
    ```
	 materials
	 semi_finished_products
	 finished_products
	 ```
    С общей абстракцией через production.

Для нашей задачи я считаю вариант А значительно правильнее, потому что пользователь сам должен иметь возможность строить
произвольные технологические цепочки, а не попадать в заранее заданные категории.

Поэтому следующий шаг:

Я предлагаю сейчас сделать не миграции, а окончательную схему именно этих таблиц:

1. production_items
2. production_operations
3. production_operation_input_specs
4. production_operation_output_specs
5. production_routes
6. production_route_steps
7. production_jobs
8. production_operation_executions
9. production_operation_inputs
10. production_operation_outputs

И отдельно определить, как ProductionItem связывается с существующими materials и material_rolls, чтобы склад и
производство не начали дублировать друг друга.
